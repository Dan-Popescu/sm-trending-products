## L1: Concurrent capture and research load

Build a bounded reproducible owned-scratch workload that exercises actual
controlled loopback acquisition/durable ingestion while real public research
reports operate on retained synthetic history. Extend existing workload/supervisor
safety rather than introduce a production execution path or arbitrary callbacks.
Prove actual overlap of useful collection and report work. Declare input products,
videos/texts, observations, retained days, arrivals, source latency, report scope
and budgets. Larger cases remain explicit opt-in finite campaigns; CI only checks
small behavioral cases. Do not relabel a tiny admitted fixture as massive capacity.

Report admitted/completed/missing/duplicate work, queue size and age, arrival/drain
and report latency, CPU, available memory/disk measurements, HTTP/object traffic,
errors and cleanup. Keep phase/process/database/whole-host resource scopes distinct;
unavailable measurements remain null. Include a matched capture-only control or
an explicitly scoped comparison. Never infer provider invoices or target capacity
from fixture timing. Preserve fixed historical report bytes/IDs under later
arrivals, and verify current admitted evidence after collection/drain. Keep cold
and warm behavior distinguishable. Enforce local synthetic state, empty owned
scratch, disabled real acquisition/providers, deadline, cumulative upload, disk
and memory-headroom bounds. Interrupted/refused cases retain known usage and
unknown in-flight work honestly, terminate owned children only, remove owned state,
and report cleanup failures. Preserve existing CLI/workload defaults and schemas.

## L2: Explicit selection candidates and governed comparisons

Prepare editable bounded illustrative policy candidates using existing
AssessmentPolicy and ValidationProtocol contracts, with meaningful declared
weights/history/missing-data differences and an explicit unvalidated status.
They are investigation strategies, not calibrated winning-product definitions.
Explain growth across days, diversity/coverage, competition, commercial margin
and delivery using existing facts and clear unknowns. Do not claim that a weight
implements a persistence/diversity rule absent from its actual kernel, and never
invent unavailable demand, supplier, geography, margin, delivery or sales.

Provide a bounded read-only operator comparison of existing governed DEVELOPMENT
attempts, through current authoritative result/source reads. Validate or explicitly
refuse differing protocol/workspace/partition/date scope/evaluation cutoff; expose
coverage/exclusions and unknown/maturing outcomes instead of ranking incomparable
samples. Compare actual existing outcome summaries and selected identities; do not
recompute counter formulas, create a second evaluator, automatically choose a
winner, open heldout outcomes to select policies, or override protocol locks.
Preserve registered/selected policies, attempts, lineage, current withdrawal,
knowledge-time and real/synthetic guards. Reads never install SQL. Keep bounded
human-readable and machine outputs accessible through existing CLI/private research
interfaces without storing raw reports in UI session state. Use guarded final
display serialization and current secrets; preserve existing default outputs.

Provide controlled native operator examples demonstrating candidate differences,
strict missingness, comparable versus refused/flagged unequal runs, invalidated
source evidence, locks/holdout restrictions and safe useful summaries. Simulations
verify software behavior; useful real selection criteria require authorized real
history and, for profit, complete reviewed commercial outcomes.
